Chapter 01

Exploring the sources

DarGlobal, explored by hand first. We walked the site the way a buyer would. Under Building Communities the menu splits into Real Estate developments (by country), Asset Management and Collaborations with brand partners. Before scaling up we took one project, Trump International Hotel & Tower Dubai, as a pilot and wrote down everything its page shows. Then we fetched one project from each menu category, and only after that every project.

The key discovery. Every DarGlobal page is a Next.js page that ships its full CMS content (Strapi) inside __NEXT_DATA__. That payload is cleaner than the visible HTML: labelled fields, original-resolution images with alt text, FAQ pairs and coordinates. We read it with adapters for the three page layouts the site uses:

  • A · /[slug], standard project pages
  • B · /rayana/…, /amaya/…, rendered client-side, so there is no visible text at all without the payload
  • C · /landing-page/[slug], campaign pages such as AIDA

Wasalt, explored the same way. The site lists rent, sale, auction, commercial, barter, projects and daily rental. We scoped the dataset to residential properties for sale in Riyadh.

Chapter 02

Collecting the data

DarGlobal

Playwright with a real Chromium

  • A visible Chromium browser driven by Playwright, one page at a time
  • Scrolls like a reader so lazy galleries and FAQ blocks render
  • Polite by design: honours robots.txt, 2-second delay, no stealth plugins or spoofing
  • Stops after 3 blocked pages in a row instead of retrying around protection
  • Saved HTML goes through one import pipeline that parses __NEXT_DATA__
73 pages → 74 records (one One of One residence is known only from its collection page)

Wasalt

ChatGPT with the TinyFish web agent

  • Wasalt's bot protection challenges automated browsers after a small request threshold
  • Playwright and Chromium were stopped, and we chose not to work around the protection
  • Listings were extracted with ChatGPT using the TinyFish agent into a structured CSV
  • Each row keeps its provenance: English and Arabic source URLs and extraction time
  • No gallery images were available in this export, so Wasalt cards show a clean placeholder
80 Riyadh residential sale listings · one CSV · 10 columns, several holding JSON

Chapter 04

Chunking strategy

The two sources have different shapes, so they are chunked differently. All numbers below are read live from the built corpus.

DarGlobal · parent–child

Too long to embed whole

A DarGlobal project page runs to a median of ~500 words and up to 1,200, and mixes facts, lifestyle copy, amenities, investment arguments and a dozen FAQs. Embedded as one vector, a question about the gym would compete with paragraphs about golf courses and payment plans. So each project is split along the page's own sections:

  • Parent: the full record, never embedded. It is stored in parents.json and powers cards, the residence drawer and "tell me about…" answers.
  • Children: one chunk per section: summary, key facts, overview, key features, amenities, why invest, location, gallery, property cards, related projects and one chunk per FAQ.
  • Every child starts with a breadcrumb such as DarGlobal > Real Estate developments > Spain > Marea > Key facts., so it reads correctly on its own.
  • Every child carries its parent's filter metadata (country, type, bedrooms, area, price flag) plus parent_id, chunk_type and a content hash.

Wasalt · one listing, one chunk

Small enough to stay whole

A Wasalt listing is short: a median of ~100 words. Splitting it would separate the price from the district and the bedroom count from the licence, which are exactly the facts a buyer combines. So the listing document is its own single child:

  • Header: title and listing ID
  • Facts sentence: type, district, zone, city, price, price per sqm, bedrooms, area, facade, age, utilities, licence
  • The description in English and Arabic, so Arabic questions match Arabic text
  • Stock lines and personal data removed; the parent record keeps the structured fields for the card

Design notes and known limits

  • No fixed-size windows. Sections follow the page's own structure, so chunks range from 14 to 343 words (median 77). Every chunk fits comfortably in text-embedding-3-small's 8,191-token limit and is embedded whole.
  • FAQs are atomic. One question and its answer per chunk is the most precise unit for "can I…", "when will…" questions.
  • Duplicates collapsed. Byte-identical pages, such as a project served at two URLs, are indexed once and kept as an alias.
  • Limit: about 200 chunks typed other are generic sections from non-property pages (about, policies, partner copy). They are longer and less focused, and they rank below property chunks for property questions.
  • Option: for a self-hosted 128-token model (multilingual MiniLM), long chunks are embedded as overlapping ~90-word windows that repeat the breadcrumb. With Upstash's hosted model this isn't needed.

Chapter 05

Index & models

Vector database
Upstash Vector
Hybrid index, serverless REST, metadata filters. Free tier: 10k queries and 10k updates a day.
Dense embedding
text-embedding-3-small
OpenAI, 1,536 dimensions, hosted by Upstash. We upload text and Upstash embeds it, so no model ships with the app.
Sparse retrieval
BM25
Scored inside Upstash on the same chunks; exact names, numbers and Arabic words match reliably.
Fusion
In-database
Upstash fuses the dense and sparse rankings; a bundled BM25 index takes over if Upstash is unreachable.
Orchestration
LangGraph
parse → retrieve → build_context → generate → verify, plus an out-of-scope branch.
Language model
OpenRouter free models
Discovered at runtime, rotated on errors with cooldowns, 40-second budget. Pin them with OPENROUTER_MODELS.
API
FastAPI
Chat, search, property detail, chunks, stats and evaluation endpoints, with a cache and a rate limit.
Configuration
3 variables
UPSTASH_VECTOR_REST_URL, UPSTASH_VECTOR_REST_TOKEN, OPENROUTER_API_KEY

Ingestion: build_index.py detects the index type and uploads each chunk's text with its metadata. Upserts are keyed by chunk ID and content hash, so re-running only changes what changed.

Answering a question

One POST /api/chat request end to end, with the offline build that feeds it.

ReceiveFastAPI validates the question (1–500 characters), rate-limits per IP and serves repeats from a one-hour cache.
UnderstandRules extract type, bedrooms, price (“under 3M”), area, purpose and location, with typo tolerance and Arabic, and spot named projects, brands and the topic.
SearchUpstash runs dense and BM25 search together over the child chunks, with the metadata filter, and fuses the rankings.

GenerateA free OpenRouter model writes a cited answer. Without one, a grounded summary is composed from the records.
VerifyEvery number must appear in the sources and every citation must exist; otherwise the grounded summary is used.

Benchmark, honestly

Loading the latest evaluation…

Read this before the numbers

  • It's a regression suite, not a real-world accuracy claim. The 165 golden questions are generated from the same records by templates ("Which country is X in?", "villas in East Riyadh"), so they're in-distribution and phrased the way the parser expects. Scores near 100% here mean "nothing broke", not "always right".
  • FAQ questions reuse the FAQ's own wording, which makes them easy for retrieval. Real users paraphrase.
  • Small samples. Some metrics rest on few questions: behaviour on 4, parse accuracy on 46. Each score shows its sample size and a 95% confidence lower bound (Wilson).
  • Run conditions matter. The stored report was produced with the configuration shown above. Answer checks are substring matches, and nothing here is human-labelled.
  • Not measured yet: paraphrased and multi-intent questions, answer helpfulness rated by people, and Upstash or LLM latency under load. Run evaluate.py --llm --judge for model-graded faithfulness.
